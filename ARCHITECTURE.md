# Shelf Life Tracking — System Architecture

Authoritative description of the Crop Protection (CP) shelf-life tracking system: what every screen does, how the frontends and backend connect, and the exact API contract. Written so the same system can be replicated for Seeds (see `docs/REPLICATION-GUIDE-SEEDS.md`).

---

## 1. System overview

Three components, all serverless, zero paid infrastructure:

| Component | Technology | Location | Role |
|---|---|---|---|
| Operator app | Static HTML/CSS/JS (localStorage + `fetch`) | `apps/operator/` | Field counting by warehouse operators (PIN login, big buttons, numpad) |
| Admin panel | Static HTML/CSS/JS + Chart.js | `apps/admin/` | Master view: dashboards, tables, monthly report, settings, data cleanup |
| Backend | Google Apps Script, runs against a Google Spreadsheet | `database/google-apps-script.gs` | REST API over Google Sheets; also runs a month-end snapshot time trigger |

There is **no server-side business logic other than the Sheets-backed API**. All reporting logic (ageing, cohort, snapshots rebuild) is implemented twice — once client-side in `admin-app.js`, once server-side in the snapshot engine — because the admin panel must work offline and the snapshots tab must be filled even when no browser is open.

**The spreadsheet is the source of truth (cloud).** Each browser keeps a full local mirror in `localStorage` so the apps work offline; syncing reconciles the two.

Architecture shape:

```
[Operator phones/tabs] ──╮                    ┌── Google Apps Script (backend)
    localStorage mirror   │  fetch (GET/POST)  │      doGet / doPost dispatchers
                          ├────────────────────┼── Google Spreadsheet
[Admin browser tabs]  ────╯                    │      tabs: transactions, inventory,
    localStorage mirror                        │             snapshots, config, dashboard
                                               │      + time trigger: autoSnapshotMonthEnd
                                               └── (1st of month, 00:00)
```

## 3. Data model

### 3.1 Spreadsheet tabs (created by `setupSheet`)

Tab schemas are defined in `database/google-apps-script.gs:34-39`.

**`transactions`** (append-mostly event ledger — the source of truth):

```
product | pack_size | production_month | expiry_month | quantity | type | operator | warehouse | client_timestamp | client_date | server_time
```

- `production_month`: one-char production year (`5` = 2025) + one-char month letter (`A`–`L`), e.g. `5A`. Year offsets are config-driven (`prodYears`).
- `expiry_month`: display form `"Jan 2027"`. Google Sheets may auto-coerce this to a Date object; the backend normalizes it back to text (`normalizeDateValue`, `google-apps-script.gs:247-253`).
- `type`: `receive` (addition) | `dispatch` (subtraction) | `adjustment` (set exact).
- `client_timestamp`: ISO string generated by the browser (`new Date().toISOString()`); **the identity key** — never changed, matched by `updateTransactions`.
- `client_date`: human display date also set client-side.
- `server_time`: appended by the backend on insert (`google-apps-script.gs:391-392`); drives the Sheets dashboard's "Recent Transactions" query.

**`inventory`** (derived/denormalized mirror — rebuilt server-side on every write):

```
product | pack_size | production_month | expiry_month | quantity | warehouse
```

Key: `product|pack_size|production_month|warehouse`.

**`snapshots`** (auto-frozen month-end closes):

```
snapshot_month | product | pack_size | production_month | expiry_month | quantity | warehouse | age_months
```

`snapshot_month` is `"YYYY-MM"` (e.g. `2026-09`); `age_months` is whole months from that month's end to the expiry month end.

**`config`**:

```
key | value
```

Two rows: `shelf-life-config` (operatorPins, expiryYears, prodYears, warehouses as JSON) and `product-list` (JSON array of `{name, pack, prefix}`).

### 3.2 localStorage keys

| Key | Writer | Purpose |
|---|---|---|
| `admin-session` | admin login | `{role:'master'}` or `{role:'officer', warehouse}` (sessionStorage) |
| `operator-data` | operator + sync | `{transactions:[], inventory:[]}` — the local mirror ledger + rebuilt inventory |
| `last-sync-ts` | sync pull | newest `client_timestamp` seen, enables delta pulls |
| `shelf-life-config` | config load/save | merged config mirror |
| `synced-products` | sync pull | cloud product list mirror (overrides the bundled master when present, `products.js:118-131`) |
| `custom-products` | admin products screen | full product array after add/edit/delete |
| `product-agi-codes` | admin | user AGI-code overrides: `{"Product|Pack":"code"}` |

`sync.js` holds the URL and prefixes all actions with `action=`.

### 4.1 GET (read) actions — `doGet`, `google-apps-script.gs:220-240`

| action | Query params | Response |
|---|---|---|
| `ping` | — | `{ok:true, time:ISO}` |
| `read` | `sheet` | Array of objects keyed by header; `[]` if headers only |
| `readFiltered` | `sheet`, `key`, `value` | First row matching `key==value`, or `null` (used for config) |
| `readSince` | `sheet`, `since` | Rows (of `transactions`) with `client_timestamp` string > `since`; falls back to `read` if empty |

Example: `?action=readFiltered&sheet=config&key=key&value=shelf-life-config`

### 4.2 POST (write) actions — `doPost`, `google-apps-script.gs:340-369`

`POST` body is always a JSON object with an `action` field. Responses are JSON.

| action | Body | Behavior |
|---|---|---|
| `batchInsert` | `{action, sheet:'transactions', rows:[[...]...]}` | Appends rows, stamps `server_time`, rebuilds inventory tab |
| `batchUpsert` | `{action, sheet, compositeKey:[...], items:[{...}]}` | Insert-or-update by composite key. Used for config + snapshots |
| `clear` | `{action}` | Deletes all data rows from transactions/inventory/snapshots, reseeds default config |
| `clearByWarehouse` | `{action, warehouse}` | Removes a warehouse's rows from all three tabs |
| `clearByDateRange` | `{action, start, end}` | Deletes transactions in date range (by `client_timestamp`), rebuilds inventory |
| `updateTransactions` | `{action, items:[{client_timestamp, product, pack_size, production_month, expiry_month, quantity}]}` | Edits a transaction **in place**, matched by `client_timestamp`; bumps `server_time`; rebuilds inventory |
| `deleteTransactions` | `{action, items:[{client_timestamp}]}` | Removes transaction rows **by `client_timestamp`**, then rebuilds inventory via shared `rebuildInventoryTab` helper |

Transaction row column order for `batchInsert` (must match `setupSheet` order exactly, `sync.js:133-146`):
`product, pack_size, production_month, expiry_month, quantity, type, operator, warehouse, client_timestamp, client_date` — the server appends `server_time`.

Upsert composite keys:
- config: `['key']`
- snapshots: `['snapshot_month','product','pack_size','production_month','expiry_month','warehouse']` (note: the caller in `saveSnapshot`, `sync.js:397`, and the snapshot engine, `google-apps-script.gs:903`, both include `expiry_month`)

## 5. Backend deep-dive (`database/google-apps-script.gs`)

### 5.1 `setupSheet` (:30-72)
Creates the four tabs if missing, writes/repairs headers, seeds the default config + empty `product-list` rows, deletes Google's blank `Sheet1`, then calls `buildDashboard`. **Run once from the editor** (and it can be re-run; headers repair is idempotent, `:49-52`).

### 5.2 `buildDashboard` (:86-208)
Creates a read-only `dashboard` tab of live `QUERY` / `COUNTIFS` / `SUMIFS` formulas: product summary, expiry buckets, warehouse summary, recent 20 transactions. Expiry-bucket date thresholds are **baked in at setup time from `now`** — re-run `setupSheet` periodically or buckets go stale (documented in the code, `:120-122`).

### 5.3 Read path (:247-327)
- `normalizeDateValue` (:247): converts Google's Date objects in `expiry_month`/`production_month` back to `"Mon YYYY"`.
- `readSheet` (:258), `readFiltered` (:278), `readSince` (:307). All keyed off header row 1.

### 5.4 `handleBatchInsert` (:381-403)
Appends rows in one `setValues` call, stamps `server_time`, and if the sheet is `transactions` calls `updateInventoryFromTransactions`.

### 5.5 `updateInventoryFromTransactions` (:421-519)
The server-side inventory reducer. Key `product|pack_size|production_month|warehouse`. `receive` adds (creating a row on first sight), `dispatch` subtracts with floor 0 and deletes the row at 0, `adjustment` sets absolute and deletes at ≤ 0. Row deletions shift the in-memory index (`:482-484`).

### 5.6 `handleBatchUpsert` (:533-585)
For each item re-reads the sheet, finds a row where every `compositeKey` col matches (string compare), updates only columns present in the item, else appends. `updated`/`inserted` counts returned. **Updating by column means a newer month's snapshot row keeps its old values for absent columns** — by construction `saveSnapshot`/snapshot engine always send full rows.

### 5.7 Clear actions (:593-683)
`handleClear` nukes the three data tabs and reseeds config (`:593-608`); `handleClearByWarehouse` keeps only rows not matching the warehouse across all three tabs (`:612-638`); `handleClearByDateRange` filters transactions by `client_timestamp` byte range then rebuilds inventory from the survivors (`:642-683`).

### 5.8 `handleUpdateTransactions` (:698-756) / `handleDeleteTransactions` (:758-804)
Both match a row by `client_timestamp` (string, exact). `handleUpdateTransactions` overwrites exactly `product, pack_size, production_month, expiry_month, quantity`, bumps `server_time`; `handleDeleteTransactions` removes the row entirely. Both then call `rebuildInventoryTab(ss, txSheet)` (extracted shared helper, same code that was inline in `handleUpdateTransactions`) — wiping the `inventory` tab and rebuilding from all surviving transactions.

### 5.9 Snapshot engine (:758-911) — the month-end freezer
- `SNAPSHOT_BD_OFFSET_MS = 6h` (:767) — Bangladesh UTC+6, no DST, so a fixed offset is correct.
- `bdMonthEndTs(y,m)` (:770): end of month `m`/`y` in BD = `Date.UTC(y, m+1, 1) - 6h - 1ms`.
- `snapshotExpiryYearMonth_` (:776): parses `"Mar 2028"` or Date → `{y, m}`.
- `snapshotAgeMonths_` (:789): whole months from snapshot close to expiry close; negative = already expired. Mirrors the admin report's `ageBucketOf`.
- `snapshotCandidateMonths_` (:796): every month (BD) from earliest to latest transaction — never empty, drives the idempotency loop.
- `snapshotBuildRows_` (:811): cumulative reduce over transactions `ts <= cutoff`, same rules as the client (`receive`+=, `dispatch`-= floor 0, `adjustment`=), first lot's expiry per key wins. Returns one row per surviving key with `snapshot_month` and `age_months`.
- `autoSnapshotMonthEnd` (:852): reads all transactions, filters to dated ones (`:866-868`), builds a set of already-stored snapshot months (`:885-891`), then for every candidate month that (a) isn't stored and (b) has ended in BD time, upserts its rows into `snapshots`. Skips months with no inventory (`:900`). Returns `{success, stored:{months,rows}}`.

### 5.10 Trigger (`installAutoSnapshotTrigger`, :915-921)
Creates a single monthly time trigger for `autoSnapshotMonthEnd` on day 1 at 00:00, deleting any prior instance first. Run once from the editor. **Independent of the web-app deployment** — it executes the editor's Head code version.

## 6. Operator app (`apps/operator/`)

Entry: `index.html` loads `products.js` → `sync.js` → `app.js`. Screen switching uses a class toggle: only the screen matching `showScreen(name)` is `active` (`app.js:52-70`).

### 6.1 Login screen — `initPinLogin`, `app.js:72-122`
- Two tabs: Operator PIN and Warehouse PIN.
- Operator logins come from config (`operatorPins`) with the pin in `state.operator`; warehouse login uses `WAREHOUSE_PINS`-style gate stored in config via `sessionStorage`-like `state`. The active warehouse is captured into `state.warehouse`; every transaction is tagged with it.

### 6.2 Product list — `renderProductList`, `app.js:178-226`
- `PRODUCTS` comes from `products.js` (bundled master, ~72 rows) but `loadSyncedProducts()` overrides it from `localStorage['synced-products']` when present (`products.js:118-131`) — cloud admin edits win.
- Rows show product name, pack size, and an AGI code badge from the `AGI_CODES` lookup (`getAgiCode`, `products.js:94-96`).
- Alpha jump bar (`renderAlphaJump`, `app.js:163`) scrolls to the first product per letter.
- Search + a product-name filter select (`initProductList`, `app.js:134-161`).

### 6.3 Count screen — `initCountScreen`, `app.js:273-467`
Sequence: select product (from the list or a quick-add) → production year buttons → month letters `A`–`L` → expiry year/month → quantity via a numpad (`state.selectedYear/Month/selectedExpiryYear/Month`, `numpadValue`) → four transaction buttons: **Receive**, **Dispatch**, **Set**, **Loose** (loose converts to a plain qty entry). `Stack` toggles influence the displayed total only.

### 6.4 `doTransaction`, `app.js:539-604` — the write path
- Validates every selector is set (`:541-548`) else a toast lists what's missing.
- **Zero-stock dispatch guard** (`:550-554`): for `type === 'dispatch'`, synchronously scans `state.inventory` for the lot key; if no stock exists locally, a blocking `confirm()` warns the operator and lets them abort (Cancel) or record the dispatch anyway (OK). Prevents the "dispatch against a lot that was never received" incident class. Advisory only — does not block legitimate stale-sync edge cases.
- Builds the transaction:
  ```
  { product, packSize, productionMonth: year+monthLetter,
    expiryMonth: "Jan 2027" (from month letter), quantity,
    type: receive|dispatch|adjustment, operator, warehouse,
    timestamp: new Date().toISOString(), date: ISO }
  ```
- Mutates the running inventory in memory using the identifier-partitioned merge (`computeInventory` semantics), then calls `syncToStorage()` (`app.js:605-611`) → `saveLocal` → the sync manager push.

### 6.5 Inventory + 12-month lists — `renderInventoryList` (`app.js:469-527`), `render12MonthList` (`app.js:652-682`)
- Scoped to `state.warehouse`.
- Grouped by `product|pack`, with a per-warehouse FEFO highlight: walking newest→oldest production lot, a lot is highlighted yellow when its qty **exceeds** the running minimum of younger lots (`app.js` same algorithm as admin `renderInventory`, `admin-app.js:1073-1082`).
- 12-month list uses `monthsUntilExpiry` (`app.js:638-643`) and `getUrgencyClass` (`app.js:644-650`): `expired`, `critical` ≤3, `warning` 4–6, `notice` 7–12, `distant` 13–18, `future` >18.

### 6.6 Auto-refresh — `startAutoRefresh`, `app.js:686-705`
Polls `syncManager.pullAll()` every 15 s when the tab is visible; stops when hidden.

## 7. Admin panel (`apps/admin/`)

Entry: `admin-panel.html` loads `admin-app.js?v=14` (CSS `?v=9`). All renders read `loadOperatorData()` (localStorage mirror) — so the panel is fully offline-capable.

### 7.1 Authentication reality (`admin-app.js:1-108`)
- `MASTER_PIN = '9504'` (:8); `WAREHOUSE_PINS = {Bogura:'2947', Chittagong:'5185', Jessore:'3639', Gazipur:'8274'}` (:9).
- Session stored in `sessionStorage['admin-session']` as `{role:'master'}` or `{role:'officer', warehouse}` (`getSession`/`setSession` :13-17, `adminLogin` :30-53).
- **Three gates** are distinct:
  - `gateCheck(action)` (:66): master bypasses; an officer must re-enter the **master PIN or their own warehouse PIN** (prompt). Used for editing transactions, revealing operator PINs.
  - `gateMaster(action)` (:84): master only; officer must give the **master PIN**. Used for product edits and central clear actions.
  - `gateWarehouse(action, warehouse)` (:98): master bypasses; else the PIN of the *target* warehouse (so deleting one warehouse's data needs that warehouse's PIN).
- `checkAdminAuth` (:19) gates app init; wrong login shows `Incorrect PIN`.
- **`normalizeWarehouses` (:119-122)** is a hardening shim: on every admin load it forces `CANONICAL_WAREHOUSES = ['Bogura','Chittagong','Jessore','Gazipur']` and re-pushes config, so foreign warehouse names from a prior project can't resurface through `mergeConfig` unions.

### 7.2 Dashboard — `renderDashboard`, `admin-app.js:508-569`
- Reads money from `opData.inventory`, filters to qty>0 with an expiry month, maps to `monthsUntilExpiry` + `getExpiryLevel`.
- Five KPI stat cards (Critical ≤3 / Warning 4-6 / Notice 7-12 / Distant 13-18 / Expired) are counts of lots per level (:524-534).
- Warehouse activity list: dots green if that warehouse has stock (:536-545).
- Recent counts: the last 5 transactions reversed (:547-558).
- Then three Chart.js charts (`renderCharts`, :616-734): Top 10 Products (bar), Stock by Batch Code (bar, by production code), Expiry Distribution (doughnut). Year/month filter pills feed `filterChartInventory` (:571-614). All charts destroyed/regenerated per render (:621).
- `renderOperatorStats` (:2280-2306) and `renderDailyTrends` (:2311-2355) round out the dashboard.

### 7.3 12/18-month expiry table — `render12M`, `:742-786`
Filter ∪ search over expiring items; sorted by months-left ascending; row + badge classes per level; `filter12M` (:788) toggles level chips.

### 7.4 Inventory table — `renderInventory`, `:1020-1104`
Product/pack group header rows, then per-lot rows with Prefix, AGI code, prod month, expiry, months-left badge, qty, warehouse. Warehouse-grouped FEFO highlight (same algorithm as operator, :1073-1082). Level chips + search. `filterInventory` (:803) toggles levels.

### 7.5 Activity log — `renderActivity`, `:840-879`
Filters: warehouse chips, type (Addition/Subtraction/Set via `typeMap`), search by product/pack/code/AGI/operator. Sorted newest-first by timestamp. `renderActivityWarehouseChips` (:824) + `filterActivityWh` (:833).

### 7.6 Edit transactions — `renderEditList`/`openEditModal`/`saveEditTransaction`/`deleteEditTransaction`, `:901-1058`
- Officer session scopes the list to their warehouse (:908).
- **Edit**: writes go server-side via `syncManager.updateTransactions` (matched by `client_timestamp`), then **forces a full pull** (`pullAllForce`) so every device converges, then re-renders everything (:1002-1011). Window header notes timestamp/type/operator/warehouse are read-only; product, pack, prod code, expiry, qty are editable.
- **Delete** (`:1017-1058`): button in modal opens `deleteEditTransaction()`. Computes an **impact preview** by replaying `computeInventory` twice (with/without the row) and shows the before/after stock in the confirm dialog. If no stock existed for the lot, the confirm states this explicitly so the officer knows it's a ledger-only cleanup. On confirm, calls `deleteTransactions` → `pullAllForce` → re-render. Same officer scoping and gate-check as Edit.

### 7.7 Monthly Report — the report engine, `:1288-1817`
This is the flagship screen. **It reads only `localStorage['operator-data']` and writes nothing.**

Snapshot model (date math):
- `monthEndOf(ym)` (:1322): last ms of a calendar month — `new Date(y, m-1, 1)` then `setMonth(getMonth()+1, 0)` at `23:59:59.999`. (Ancient bug: `-1` was missing before the `v11` fix, see git `6a96924`.)
- `monthStartOf(ym)` (:1330) and `parseEntryDate(tx)` (:1315): timestamps or falls back to `tx.date`; **`0` for undated transactions**.
- `rebuildInventoryAt(cutoffTs, anchorEnd)` (:1340-1361): reruns the full ledger onto a cutoff using the operator's exact merge rules; **undated (`ts===0`) rows are anchored to the *current-month* cutoff only** (`:1343`) — so during a first month of input, last month's snapshot is correctly 0.
- `computeMonthSnapshots` (:1374-1404): picks `cmMonth` = latest dated month (or the picker), `lmMonth` = one before; returns `lmSnapshot`/`cmSnapshot` plus `lmHasRecords`, `isFirstMonth`, `skipped`.

Ageing summary — `renderAgeingSummary` (:1485-1575):
- Two columns of buckets via `ageBucketOf(expiryStr, refEnd)` (:1415-1426): `expired` <0, `crit` ≤3, `warn` ≤6, `notc` ≤12, `dist` ≤18, `futr` >18.
- Strip: current-month ctns, at-risk ≤12mo (absolute + %), expired.
- Six clickable category cards (qty now, qty last month, share %) → `showAgeingDrilldown(bucket)` (:1577-1592).
- Per-row: LM qty | CM qty | Change | Change % | share bar. Change % shows `New` when LM was 0 (:1561-1566). Lots without an expiry date are excluded from bucketing but counted in totals, and reported in an excluded-note (`:1540-1552`).
- `exportAgeingSummary` (:1594-1613).

Cohort follow-up — `buildCohort`/`renderCohortFollowup` (:1619-1731):
- Cohort = every SKU (`product|pack|productionMonth`) that was ≤12-month risk **last month** (`:1624-1633`). `dist`/`futr` excluded.
- **Baseline month mode** (:1634-1645): if no last-month cohort exists AND this is the first month of records, it builds from current-month at-risk SKUs with `lmQty=0` so the screen still shows something meaningful.
- For each cohort row: `cmQty` from the cm snapshot (+ any tx touching the key in the current month, `:1652-1658`), `net = cmQty - lmQty`, status: `Fully cleared` / `Absent in CM — verify` (cleared AND no tx touched it) / `Exposure increased` / `Exposure reduced` / `No change`.
- KPI chips (`cohortKpiChip`, :1691): Risk Batches, LM Risk Qty, CM Remaining, Qty Reduction (+%), Fully Cleared, Increased Exposure; baseline month neutralizes reduction/increased.
- Chips are **clickable** (`showCohortChipBreakdown(kind)`, :1733-1778) → drilldown modal lists exactly the SKUs behind that chip (uses an 8-column thead, restored by `closeDrilldown` :1964-1967).
- Rows clickable → `showCohortDetail` (:1780-1801) per-warehouse LM→CM breakdown.
- `exportCohortFollowup` (:1803-1813).

### 7.8 Country summary — `renderCountrySummary`, `:1821-1879`
Aggregates inventory per `product|pack` across all warehouses; columns Expired / ≤3 / 4-6 / 7-12 / ≤12 subtotal / 13-18 / Future / Total; search matches product/pack/AGI/prod-codes; closest-expiry drives sort. `showCountryDetail` (:1881-1903) lists lots. `exportCountrySummary` (:1905-1933).

### 7.9 Products — `renderProducts`/`openProductModal`/`saveProduct`/`deleteProduct`, `:1111-1197`
Master-only edits (`gateMaster('change products')`). Add/delete/edit updates `PRODUCTS`, the `product-agi-codes` override map (invalidated when name/pack changes), `localStorage['custom-products']`, then `syncProducts()` pushes to cloud. Officer sessions see read-only (`canEdit` via `!sessionScope()`, :1120).

### 7.10 Settings — `renderSettings`, `:1972-2167`
- Operator PIN list (name, masked/revealed pin, warehouse); reveal/remove scoped to own warehouse (:2025-2048, :2050-2064). Adding a PIN rejects duplicates, warehouse/master-pin collisions, non-4-digit values (:2066-2086). All changes go through `saveConfig`.
- Expiry years / production years selects with live previews; bumping rd ranges (`saveExpiryYears`/`saveProdYears` :2099-2119).
- Warehouse list with per-warehouse `Delete Data` + remove; add warehouse (:2121-2157). `resetConfig` restores `DEFAULT_CONFIG` (:2159-2167).

### 7.11 Danger zone — `:2172-2275`
- `clearLocalData` (:2172): wipes this browser's `operator-data` (two-step confirm; notes auto-sync may redownload).
- `clearLocalDataForWarehouse` (:2192): filters a warehouse out of local txs+inventory.
- `clearCloudData` (:2208): master gate; calls `syncManager.clearCloud()` (must come after `localStorage` wipe it, or sync re-uploads).

- Modals close on overlay click (:2433-2441); app boots only if `checkAdminAuth()` passes (:2475-2477).

## 8. Sync architecture (`apps/operator/sync.js`, exposed as `window.syncManager`)

Shared by both apps (admin panel includes the same `sync.js`). It is a full local-first mirror, not a cache.

- `apiGet`/`apiPost` (:28-44): thin `fetch` wrappers with JSON.
- `computeInventory(transactions)` (:14-26): the canonical local reducer — `receive` +=, `dispatch` −= floor 0, `adjustment` = ; rows at 0 dropped. **Every screen's "current stock" is this pure function over the ledger.**
- `init` (:71-77): registers `online` → `syncAll`.
- `saveLocal` (:94-117): persists and stamps `synced` flags, then triggers a push when online.
- `syncAll` (:123-171): pushes all `!synced` transactions as one `batchInsert`, marks them synced in local, notifies callbacks; retry-on-change flag if a sync is already running.
- `pullAll(force)` (:199-296): full pull (no `last-sync-ts`) replaces cloud transactions then re-appends local unsynced ones (`:211-241`); delta pull (`readSince`) merges by `client_timestamp` key (`:242-270`). Recomputes inventory, writes mirror, updates `last-sync-ts`, sets `syncStatus`.
- Config pull/push (:306-360): `mergeConfig` (:51-68) unions operatorPins (by pin) and warehouses, cloud wins on year ranges — prevents multi-PC last-writer-wins wiping PINs.
- `updateTransactions`, `deleteTransactions`, `saveSnapshot`, `getMonthlySnapshots`, `clearCloud`, `clearByWarehouse`, `clearByDateRange` (:364-460): thin wrappers over the matching POST actions.
- `computeInventory`: exposed on `syncManager` (`sync.js:82`); shared by both apps; admin uses it for the delete-impact preview.

**Merge semantics** (critical, reproduced exactly by `rebuildInventoryAt`):
1. Transactions are partitioned by identity (`client_timestamp`).
2. History-ordered reduce over those partitions.
3. `receive` += / `dispatch` −= floor 0 / `adjustment` =.
4. Row survives iff final qty > 0.

## 10. Deployment & versioning

1. **Backend**: edit `google-apps-script.gs` → paste into the Apps Script editor → save → *Deploy → Manage deployments → edit the web-app deployment* (or new deployment) → copy URL into `sync.js` `APPS_SCRIPT_URL` (`sync.js:4`).
2. **Frontend**: edit files, bump the cache-bust token in `admin-panel.html` / `index.html` references (currently `admin-app.js?v=14`, `admin-style.css?v=9`), commit, push to the hosting (GitHub Pages / gstack deploys to the `main` branch `docs`/site for this project).
3. **Live deploy behavior**: the deployed web-app URL serves the *deployed* backend but the *latest* frontend HTML/JS. The **time trigger runs the editor's Head script version** — independent of the deployment. So a backlog of month-end snapshots only needs the backend deployed once.
4. **Version history** (git): `dcf02a9` v10 Change columns → `6a96924` v11 month `-1` fix → `2cf95b3` v12 baseline cohort fallback → `ae11705` v13 baseline KPI gate → `abc4b1c` snapshot trigger → `045151d` v14 clickable cohort chips.

## 11. Known edges and operational notes

- The deployed backend can lag the repo until re-deployed; the monthly report is unaffected (it's pure client-side), and the snapshot trigger uses Head code.
- `buildDashboard`'s expiry thresholds reference the setup date; re-run `setupSheet` when year boundaries matter.
- The admin panel's `inventory` tab and the Sheets `inventory` tab are independently derived from the same ledger; they can disagree transiently until a pull/rebuild completes — the ledger (`transactions`) is always authoritative.
- `clearCloudData` without a subsequent config/product re-push lets the next `pullAll` resurrect rows (documented in the UI alert too).
